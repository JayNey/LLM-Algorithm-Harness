## Context

项目现有多个策略类（VanillaStrategy, ChainOfThoughtStrategy, ReflexionStrategy, SelfConsistencyStrategy, MultiRoundFeedbackStrategy）都继承自 `StrategyBase`，该基类提供 LLM 生成、代码提取、沙箱执行等通用能力。现有策略主要采用线性或简单迭代模式，缺少对多分支探索的系统支持。

Tree of Thoughts (ToT) 需要在每个推理节点生成多个候选方案，维护一个搜索树结构，并对节点进行质量评估和剪枝。这要求引入新的数据结构（ThoughtNode）和搜索算法（BFS/DFS），同时保持与现有框架的兼容性。

## Goals / Non-Goals

**Goals:**
- 实现完整的 ToT 搜索树结构，支持多分支生成和遍历
- 提供可配置的搜索策略（BFS/DFS）和剪枝机制
- 复用现有 StrategyBase 的 LLM 生成和沙箱执行能力
- 保持与现有策略配置、日志、预算管理的一致性
- 通过单元测试验证核心逻辑（覆盖率 >= 90%）

**Non-Goals:**
- 不实现超出 BFS/DFS 的高级搜索算法（如 A*、蒙特卡洛树搜索）
- 不改变现有策略的接口或行为
- 不在本阶段进行大规模性能优化（如并行评估、缓存）
- 不训练独立的评估模型（使用 LLM 进行质量评分）

## Decisions

### 1. 数据结构：ThoughtNode 作为树节点

**决策**：使用 `@dataclass` 定义 `ThoughtNode`，包含 depth、thought、code_snippet、quality_score、children、parent 字段。

**理由**：
- 使用 dataclass 简化数据类定义，自动生成 `__init__`、`__repr__`
- 显式的 parent 引用支持从叶子节点回溯到根节点
- quality_score (float) 便于比较和排序
- children (List[ThoughtNode]) 支持任意分支数

**备选方案**：
- 使用普通类：需要手写初始化代码，verbosity 更高
- 使用字典：缺少类型检查，容易出错
- 不存储 parent：回溯时需要额外搜索

### 2. 搜索实现：使用队列（BFS）和栈（DFS）

**决策**：
- BFS：使用 `collections.deque` 作为队列，FIFO 顺序
- DFS：使用 `list` 作为栈，LIFO 顺序

**理由**：
- deque 的 `popleft()` 操作是 O(1)，适合 BFS
- list 的 `pop()` 操作是 O(1)，适合 DFS
- 标准库实现，无需引入外部依赖
- 代码清晰，易于理解和测试

**备选方案**：
- 递归实现 DFS：可能导致栈溢出（Python 默认递归深度限制 ~1000）
- 优先队列（heapq）：适合 A* 等启发式搜索，但本阶段不需要

### 3. 质量评估：通过 LLM 进行评分

**决策**：每个节点的质量评分通过向 LLM 发送评估 prompt 获得，prompt 包含问题描述、当前思考内容和代码片段，要求 LLM 返回 0-1 之间的分数。

**理由**：
- 复用现有 `self.generate()` 方法，无需外部评估模型
- LLM 可以理解自然语言推理过程，评估逻辑正确性
- 配置简单，用户无需准备额外训练数据

**备选方案**：
- 基于规则的评分（如代码长度、语法复杂度）：无法捕捉语义正确性
- 执行测试用例作为评分：成本高，且可见测试数量有限
- 训练独立评估器：需要大量标注数据，超出本阶段范围

**Trade-off**：LLM 评估增加 API 调用成本和延迟，但提供更准确的质量判断。

### 4. 剪枝策略：基于固定阈值

**决策**：在生成分支后，对所有子节点评分，过滤掉 `quality_score < pruning_threshold` 的节点。

**理由**：
- 简单直观，用户可通过配置调整剪枝力度
- 在节点扩展时立即剪枝，避免浪费后续搜索资源
- 与 BFS/DFS 正交，不影响搜索顺序

**备选方案**：
- 相对剪枝（如保留前 K 个高分节点）：需要跨节点比较，实现复杂
- 动态阈值（如基于父节点分数）：难以调参，不够透明
- 延迟剪枝（搜索结束后筛选）：浪费计算资源

### 5. 代码生成：每个节点独立生成代码

**决策**：在生成每个思考节点时，prompt 同时要求 LLM 输出当前阶段的代码片段，使用 `self.extract_code()` 提取。

**理由**：
- 符合 ToT 论文的"每个思考步骤对应一个部分解"的设计
- 叶子节点的代码可以直接作为最终解提交
- 便于评估时结合代码和推理文本

**备选方案**：
- 只在叶子节点生成完整代码：中间节点质量难以评估
- 拼接所有节点的代码片段：可能产生重复或不一致

### 6. 最终解选择：选择最高分叶子节点

**决策**：搜索结束后，从所有已探索的叶子节点中选择 quality_score 最高的节点，返回其 code_snippet。

**理由**：
- quality_score 已经综合评估了推理质量和代码正确性
- 简单有效，无需额外启发式规则

**备选方案**：
- 执行所有叶子节点代码，选择通过测试的：增加沙箱调用成本
- 加权多个高分节点的代码：代码合并语义复杂

## Risks / Trade-offs

**[Risk]** LLM 评估不稳定，同一节点多次评分可能不一致  
→ **Mitigation**: 在配置中支持温度参数，测试时使用较低温度；未来可考虑多次采样取平均

**[Risk]** 分支因子和深度设置不当导致搜索空间爆炸  
→ **Mitigation**: 提供合理默认值（branching_factor=3, max_depth=4），并在文档中给出调参建议；实施剪枝控制节点数

**[Risk]** API 调用成本高（每个节点生成 + 评估 = 2 次调用）  
→ **Mitigation**: 通过剪枝减少无效节点；用户可配置 max_depth 和 branching_factor 控制预算；记录成本供用户监控

**[Risk]** 代码片段拼接可能不完整或重复  
→ **Mitigation**: Prompt 设计时明确要求每个节点生成"当前步骤的完整逻辑"，而非增量片段；通过测试验证代码质量

**[Risk]** 搜索未能找到正确解（所有分支被剪枝或达到深度上限）  
→ **Mitigation**: 返回清晰的失败信息，包含已探索节点数和最高分数；用户可根据日志调整配置重试

**[Trade-off]** 相比简单策略（如 Vanilla、CoT），ToT 的 API 调用量和延迟显著增加，但提供了更高的准确率潜力  
→ 适用场景：复杂 hard 题目；不适合简单题目或低预算场景

**[Trade-off]** 当前设计不支持并行评估多个节点，顺序处理限制了速度  
→ 未来优化：可引入异步 LLM 调用或批处理

## Migration Plan

**部署步骤**：
1. 合并 PR 后，新增的 `TreeOfThoughtsStrategy` 自动注册到策略工厂
2. 用户在配置文件中添加 ToT 策略配置（参考文档示例）
3. 运行测试验证策略行为
4. 逐步在 hard 难度题目上启用 ToT 并监控成本和准确率

**回滚策略**：
- ToT 作为新增策略，不影响现有策略
- 如发现问题，用户只需在配置中移除 ToT 策略项，回退到原有策略即可
- 代码无破坏性变更，可直接 revert commit

**监控指标**：
- 每个问题的 API 调用次数（应显著高于单次策略）
- ToT vs 其他策略的准确率对比（在 hard 题目子集上）
- 平均搜索深度和剪枝率

## Open Questions

无需在实现前解决的问题（可在后续迭代中改进）：
- 是否需要支持自适应剪枝阈值（如根据已探索节点动态调整）？
- 是否需要引入节点缓存（避免重复评估相同思考内容）？
- 是否需要提供可视化工具展示搜索树（便于调试和分析）？
