## Context

现有策略架构：
- 所有策略继承 `StrategyBase`，实现 `execute(problem: Problem) -> ExecutionResult`
- `StrategyBase` 提供 `generate()`, `extract_code()`, `create_iteration_result()` 等辅助方法
- 现有策略（Vanilla, CoT, Multi-Round Feedback）都是单解策略
- `ExecutionResult` 和 `IterationResult` 模型已支持记录多轮迭代

Self-Consistency 需要并行生成多个候选解并投票，这与现有单解模式不同。

## Goals / Non-Goals

**Goals:**
- 实现 Self-Consistency 策略，支持可配置的候选数量（默认 5）
- 对所有候选解执行测试，统计通过的结果
- 选择出现频率最高的正确答案作为最终结果
- 记录每个候选解的详细信息（代码、测试结果、投票统计）
- 集成到现有评测和报告流程

**Non-Goals:**
- 不实现加权投票（所有候选解权重相同）
- 不实现候选解的语义相似度聚类（简单的代码字符串比较）
- 不优化并行执行性能（顺序生成和测试即可）

## Decisions

### 1. 投票机制：基于代码字符串匹配

**决策**：对通过测试的候选解，按代码字符串完全匹配进行分组计数，选择频率最高的代码。

**理由**：
- 简单直接，易于实现和调试
- 代码算法题的正确答案通常有限（不同变量名也算不同答案）
- 避免语义相似度的复杂性和不确定性

**备选方案**：
- AST 语义比较：过于复杂，且对算法题意义不大
- 输出结果比较：测试用例已经验证正确性，代码级投票更直接

### 2. 候选解生成：高温度顺序生成

**决策**：使用较高的 temperature（默认 0.8）顺序生成 N 个候选解。

**理由**：
- 高温度增加多样性，避免生成相同答案
- 顺序生成简化实现，无需处理并发
- LLM provider 通常限制并发请求

**备选方案**：
- 低温度：会降低多样性，Self-Consistency 效果打折
- 并行生成：复杂度高，收益有限

### 3. 数据模型扩展：复用现有结构

**决策**：使用 `ExecutionResult.iterations` 记录每个候选解，新增可选字段记录投票统计。

**理由**：
- 现有模型已支持多轮迭代，Self-Consistency 的多个候选解可以映射为"并行迭代"
- 最小化模型变更，兼容现有报告和序列化逻辑
- 投票统计作为元数据添加，不影响现有字段语义

**备选方案**：
- 创建新的 `SelfConsistencyResult` 模型：过度设计，增加序列化复杂度

### 4. 失败处理：部分成功也返回结果

**决策**：只要有 ≥1 个候选解通过测试，就返回成功；全部失败才标记失败。

**理由**：
- Self-Consistency 的核心价值是从多个尝试中选出正确答案
- 即使只有 1/5 通过，也比完全失败好
- 投票统计会记录通过率，供后续分析

## Risks / Trade-offs

**[风险] Token 消耗 N 倍增长** → 在配置中明确标注成本，默认 N=5 平衡效果和成本；用户可根据预算调整

**[风险] 生成时间延长** → 顺序生成会线性增加时间，N=5 时约为 Vanilla 的 5 倍；文档中说明适用场景（准确率优先）

**[权衡] 简单投票 vs. 语义聚类** → 简单投票可能低估语义相同但格式不同的答案频率；但实现简单，首版足够

**[权衡] 高温度多样性 vs. 个别低质量候选** → 高温度会产生部分低质量解；但投票机制会过滤掉，整体准确率仍提升
