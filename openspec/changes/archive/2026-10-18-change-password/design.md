## Context

个人资料已能读取并修改用户名和邮箱。口令以哈希存在 `auth_users.password_hash`，登录用同一套校验。访问令牌失效时，前端 HTTP 客户端会把 401 当成刷新信号。见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 用现有口令哈希更新当前用户的密码
- 当前密码错误不触发访问令牌刷新
- 资料页在发请求前完成长度和确认密码校验

**Non-Goals:**

- 不撤销其他会话，不强制重新登录
- 不增加忘记密码、邮件验证、角色或头像
- 不改 `password_hash` 的表结构

## Decisions

### 1. 独立的修改密码请求

新增 `POST /api/v1/users/me/password`，正文只有 `current_password` 和 `new_password`。成功返回 204。当前密码不匹配返回 400，不返回 401。新密码沿用注册的 12–1024 长度限制。

备选是把密码放进现有 `PATCH /users/me`。那个接口今天只更新用户名和邮箱，混入密码后，资料保存和口令更换无法分开失败。

### 2. 成功后保持当前会话

只替换当前用户的口令哈希。当前 access token 和 refresh token 继续可用。

备选是修改后撤销全部会话。Issue #161 只要求能改密码，强制登出会改变现有会话行为。

### 3. 资料页使用单独表单

密码表单放在现有资料表单下面，不和用户名、邮箱一起提交。三个密码框都不显示明文。客户端复用注册的长度和确认密码规则；当前密码为空时不发请求。成功或当前密码不正确时清空三个密码字段。

## Risks / Trade-offs

- [400 与请求体校验共用状态码] → 当前密码不正确使用固定中文结果，页面只认这一种失败；长度错误仍走现有「请求无效」
- [其他设备上的旧会话仍然有效] → 本变更不撤销会话；需要失效时另行设计
- [口令哈希可被同库读取] → 响应和资料对象继续不包含哈希或明文
