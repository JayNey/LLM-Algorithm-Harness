## Context

当前系统已有 `src/reporting/chart_generator.py` 用于生成各类图表，`src/models.py` 中 Problem 模型包含 tags 字段可用于问题分类。报告生成流程在 `src/reporting/html_generator.py` 和 `src/experiment_panel.py` 中完成。

现有架构使用 matplotlib 生成图表并返回 base64 编码的 PNG，通过 ChartGenerator 类统一管理。

## Goals / Non-Goals

**Goals:**
- 新增能力维度统计和雷达图生成功能，扩展现有报告能力
- 复用现有 matplotlib 基础设施和图表生成模式
- 支持单模型报告和多模型对比场景
- 保持向后兼容，无雷达图数据时不影响现有报告

**Non-Goals:**
- 不改变问题数据模型的 tags 字段结构
- 不支持用户自定义维度（初版使用硬编码维度）
- 不提供交互式雷达图（保持静态 PNG 输出）

## Decisions

### D1: 维度定义方式

**决策**: 使用硬编码的维度映射字典，将 Problem.tags 映射到预定义的算法类型。

**理由**: 
- 简化初版实现，避免配置文件复杂度
- tags 已经存在且稳定，无需修改问题数据结构
- 映射逻辑集中管理，便于后续扩展

**备选方案**: 
- 配置文件定义维度：增加配置复杂度，但更灵活
- 使用 LLM 自动分类：不确定性高，性能开销大

### D2: 模块划分

**决策**: 新增 `src/reporting/capability_profiler.py` 独立模块处理维度统计，在 `ChartGenerator` 中添加雷达图生成方法。

**理由**:
- 单一职责：capability_profiler 负责数据聚合，ChartGenerator 负责可视化
- 复用现有架构：ChartGenerator 已有图表生成基础设施
- 便于测试和维护

**备选方案**:
- 全部放入 ChartGenerator：职责混乱，类过于庞大
- 独立的 radar_chart.py：过度拆分，功能单一

### D3: 雷达图实现

**决策**: 使用 matplotlib 的极坐标投影 (projection='polar') 绘制雷达图。

**理由**:
- 原生支持，无需额外依赖
- 与现有 ChartGenerator 技术栈一致
- 社区成熟方案，示例丰富

**备选方案**:
- plotly: 交互式但引入新依赖，与现有架构不一致
- 手动计算坐标: 实现复杂，易出错

### D4: 多模型对比方式

**决策**: 在同一雷达图上叠加多个模型的能力轮廓，使用不同颜色和透明度区分。

**理由**:
- 直观对比，用户可快速识别强弱分布差异
- 充分利用雷达图的对比优势
- 避免生成多张独立图表占用报告空间

**备选方案**:
- 并排独立雷达图：难以直接对比
- 差异热力图：失去维度的极坐标直观性

### D5: 问题归类逻辑

**决策**: 一个问题可归属多个维度，按 tags 包含关系判断。

**理由**:
- 算法问题常涉及多个领域（如图 + DP）
- 避免强制单一分类的信息损失
- 维度统计时分母独立计算，不会重复计数

**备选方案**:
- 单一分类：信息损失，难以处理复合问题
- 主次分类：增加复杂度，收益有限

## Risks / Trade-offs

**[Risk]** 硬编码维度映射可能无法覆盖所有 tags  
→ **Mitigation**: 新增 "Other" 维度兜底，未匹配 tags 的问题计入该维度；后续可通过配置文件扩展映射规则

**[Risk]** 维度数量过多时雷达图可读性下降  
→ **Mitigation**: 初版限制 6-8 个核心维度；若需扩展，考虑分组或筛选机制

**[Risk]** 问题数量分布不均可能导致某些维度样本过少  
→ **Mitigation**: 在雷达图或分析文本中标注每个维度的题目数量，避免误导性结论

**[Risk]** 多模型叠加时颜色和标签可能重叠  
→ **Mitigation**: 使用透明度、不同线型（实线/虚线）和清晰的图例；限制同时对比的模型数量（建议 ≤ 4）

**[Trade-off]** 硬编码维度 vs 配置化  
→ 初版简化实现，牺牲灵活性换取开发速度；实际使用中如需自定义维度，可在后续迭代中改为配置驱动

**[Trade-off]** 静态 PNG vs 交互式图表  
→ 保持与现有报告格式一致，牺牲交互性换取兼容性和简洁性
