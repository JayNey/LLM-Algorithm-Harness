## Context

当前系统已有完善的代码质量分析能力（`src/code_quality/`），包含 `CodeQualityMetrics` 模型，可计算时间复杂度、空间复杂度、可读性和风格一致性。`IterationResult` 模型记录每轮迭代的执行数据，但不包含代码质量指标。

`MultiRoundFeedbackStrategy` 执行多轮迭代，每轮生成代码、执行测试、提供反馈。现有报告生成逻辑（`src/experiment_report.py`）生成实验对比报告，但不包含代码质量演化分析。

## Goals / Non-Goals

**Goals:**
- 复用现有 `CodeQualityMetrics` 计算能力，无需重新实现质量分析
- 在 `IterationResult` 中添加质量指标字段，最小化侵入性
- 新建独立的演化分析模块，与现有报告生成解耦
- 生成可视化趋势图表，支持单一和聚合分析
- 识别质量下降迭代，提供规则化原因分析

**Non-Goals:**
- 不修改现有 `CodeQualityMetrics` 的计算逻辑
- 不影响非多轮策略的执行和报告
- 不实现实时监控或在线分析（仅事后分析）
- 不对历史数据进行回溯分析（仅对新运行的实验生效）

## Decisions

### 1. 质量指标存储位置
**决策：** 在 `IterationResult` 模型中添加可选的 `code_quality` 字段（类型 `CodeQualityMetrics | None`）。

**理由：**
- `IterationResult` 是每轮迭代的自然数据容器
- 可选字段保持向后兼容，不影响现有数据
- 避免创建新的并行数据结构

**备选方案：** 创建独立的 `EvolutionRecord` 模型 → 被拒绝，因为会引入数据同步和关联复杂度

### 2. 质量指标计算时机
**决策：** 在 `MultiRoundFeedbackStrategy.execute()` 中，每轮迭代成功提取代码后，立即调用代码质量分析并存储结果。

**理由：**
- 最小化代码修改，集中在策略执行逻辑
- 失败时自然跳过（代码提取失败或 LLM 错误）
- 不影响沙箱执行的关键路径

**备选方案：** 事后批量分析 → 被拒绝，因为无法复用迭代过程中已计算的指标

### 3. 演化分析模块设计
**决策：** 创建独立的 `src/analysis/evolution.py` 模块，提供：
- `EvolutionAnalyzer` 类：分析 `ExecutionResult` 的迭代序列
- `identify_quality_drops()` 方法：识别质量下降点
- `analyze_drop_reason()` 方法：规则化原因分析
- `generate_evolution_chart()` 方法：生成趋势图表
- `generate_evolution_report()` 方法：生成文本报告

**理由：**
- 单一职责，与报告生成解耦
- 可独立测试和复用
- 支持命令行工具和 API 调用

**备选方案：** 直接在 `experiment_report.py` 中添加逻辑 → 被拒绝，因为会使报告生成模块过于臃肿

### 4. 质量下降判定策略
**决策：** 使用相对变化阈值 + 绝对阈值的组合策略：
- 单一指标：相比上一轮下降超过 15% 标记为下降
- 综合分数：相比上一轮下降超过 10 分（满分 100）标记为下降
- 第一轮迭代不判定（无基线）

**理由：**
- 相对阈值适应不同复杂度水平的代码
- 绝对阈值避免微小波动的误报
- 保守的阈值减少噪音

**备选方案：** 仅使用相对变化 → 被拒绝，因为小基数时会产生大量误报

### 5. 图表生成工具
**决策：** 使用 `matplotlib` 生成静态 PNG 图表，保存到实验输出目录。

**理由：**
- 与现有 `reporting/capability_radar` 一致
- 不依赖外部服务，离线可用
- 易于集成到 HTML 报告

**备选方案：** Plotly 交互式图表 → 推迟，可作为未来增强

### 6. 原因分析规则
**决策：** 基于规则的启发式分析，检查：
- 复杂度上升 + 测试通过率提高 → "过度优化"
- 代码行数显著增加 + 风格得分下降 → "代码膨胀"
- 沙箱执行失败 → 按失败类型映射（语法错误、运行时错误等）
- 多指标同时下降 → "综合质量下降"

**理由：**
- 简单、可解释、易维护
- 无需机器学习或大量历史数据
- 覆盖最常见的质量下降模式

**备选方案：** LLM 驱动的自然语言分析 → 被拒绝，因为增加成本和延迟，且难以保证一致性

### 7. 报告集成方式
**决策：** 在 `experiment_report.py` 中添加 `_generate_evolution_section()` 方法，调用 `EvolutionAnalyzer` 并在报告中插入新章节。

**理由：**
- 渐进式增强现有报告
- 仅对多轮策略生成该章节
- 不破坏现有报告结构

## Risks / Trade-offs

**[Risk 1]** 质量指标计算失败可能导致部分迭代缺失质量数据
- **Mitigation:** 将质量分析包裹在 try-except 中，失败时记录错误但不终止迭代

**[Risk 2]** 质量指标计算增加每轮迭代的开销（~100-500ms）
- **Mitigation:** 
  - 质量分析在沙箱执行后异步执行，不阻塞关键路径
  - 提供配置开关，允许用户禁用演化分析以加速实验

**[Risk 3]** 规则化原因分析可能不准确或遗漏复杂场景
- **Mitigation:** 
  - 原因分析仅作为提示，不影响实验结果
  - 在报告中标注为"自动分析建议"
  - 支持用户自定义分析规则

**[Risk 4]** 图表文件可能占用较多磁盘空间（大规模实验）
- **Mitigation:** 
  - 默认生成 PNG，使用合理的 DPI 和尺寸
  - 提供配置选项跳过图表生成（仅保留数据）

**[Trade-off 1]** 仅对新运行的实验生效，历史数据无法回溯分析
- **Justification:** 历史数据缺失质量指标，回溯计算成本高且价值有限

**[Trade-off 2]** 演化分析增加了数据模型的复杂度
- **Justification:** 可选字段设计保持向后兼容，新功能的价值超过复杂度成本

## Migration Plan

**部署步骤：**
1. 扩展 `IterationResult` 模型，添加 `code_quality` 字段
2. 修改 `MultiRoundFeedbackStrategy`，在每轮迭代后计算质量指标
3. 实现 `src/analysis/evolution.py` 模块
4. 扩展 `experiment_report.py`，集成演化分析章节
5. 添加单元测试和集成测试
6. 更新文档，说明新功能和配置选项

**向后兼容：**
- 现有实验结果（无 `code_quality` 字段）可正常加载
- 演化分析自动跳过缺失质量数据的迭代
- 非多轮策略的报告不变

**回滚策略：**
- 移除 `IterationResult.code_quality` 字段（数据库/JSON 中可保留但不读取）
- 移除报告中的演化分析章节
- 恢复 `MultiRoundFeedbackStrategy` 到不计算质量指标的版本
