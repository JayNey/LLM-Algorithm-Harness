# 已入队评估删除保护设计

## Context

动机与范围见 [proposal.md](proposal.md)，行为契约见 [delta spec](specs/api/evaluation-execution/spec.md)。当前 `delete_evaluation` 在两个事务间调用文件清理，仅检查业务状态；`can_delete` 同样忽略活动任务。提交已通过 TaskManager 的用户级数据库准入锁串行化，worker 已有覆盖在途调用的跨进程执行锁。

## Goals / Non-Goals

复用既有数据库锁、执行权和文件删除机制，封闭删除与提交的竞争窗口。持久化能力投影不探测文件锁；并发状态变化和执行尚未停止仍由删除入口最终判定。不增加取消协议、表结构或历史数据修复。

## Decisions

1. **拒绝删除活动任务。** 不在删除内部隐式取消：取消提交并不表示在途模型调用已经停止。保留用户先取消、停止后再删除的路径；异步删除服务入口也复用同一保护。
2. **拆出并复用准入事务锁。** 将 TaskManager 既有 SQLite 写锁 / PostgreSQL 用户级 advisory transaction lock 与额度计数分离；提交继续先取锁再计数，删除只取锁，不因用户已满额度而无法删除。
3. **保护覆盖清理和最终删除。** 先确认所有者，取用户准入锁后重新读取业务与关联任务，以所有者、实体和任务类型核实关联活动状态；检查业务状态，再取得非阻塞执行权。锁持续覆盖清理与业务删除提交。新提交在锁后重新判定记录存在性与关联状态，失去竞争时回滚候选且不发布消息。采用非阻塞执行锁以兼容现有恢复路径的锁顺序。
4. **状态投影一致。** 在既有 `can_delete` 业务条件上增加活动任务保护，沿用列表批量加载，避免 N+1 查询和 broker 读取。最终删除拒绝所有关联活动任务，不仅信任可能过期的单个链接。
5. **终态和文件兼容。** 保留既有结果级联删除、文件注册删除标记和延迟产物防复活机制；终态任务保留或按既有入口规则清理，不能删除活动任务来伪造额度释放。

## Risks / Trade-offs

- 文件库与业务库无法构成单一 ACID 事务：保护保证活动任务拒绝先于清理，清理异常保留评估供重试；沿用现有文件删除的幂等语义。
- 清理期间持有数据库锁会延长同用户提交等待：仅覆盖删除必要操作，使用事件驱动的并发回归验证，不引入轮询或额外模型调用。
- SQLite 与 PostgreSQL 锁原语不同：以实际 SQLite 并发回归及 PostgreSQL 锁 SQL/顺序契约检查覆盖；真实 PostgreSQL 如环境不可用，在验证报告中明确边界。

## Validation

先写并运行回归复现原缺陷，再实现。覆盖活动状态与归属矩阵、列表/详情/异步投影、入队后 HTTP 删除拒绝且无清理、并发竞争两种顺序、取消但执行未停、停止后删除的结果/文件/额度，以及清理异常重试。运行受影响评估、任务准入、文件及 worker 测试和格式检查，完整验证 delta spec 一致性。

## Migration Plan

无需数据迁移；部署服务变更即可。回退可还原本次代码，但会重新暴露 Issue #511，因此正常情况下优先修正回归。历史孤立任务不在本次自动清理范围。
