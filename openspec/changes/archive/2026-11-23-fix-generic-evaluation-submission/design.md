# 技术设计

## Context

通用路由直接调用 TaskManager.enqueue_task，没有业务关联回调；EvaluationService.start_evaluation 已校验所有者、pending 状态与重复入队，使用条件更新占位，并在发布前提交 Evaluation 和 AsyncTask。评估专用路由还负责校验凭据所有权及记录启动审计。

## Decisions

1. 通用入口 evaluation 分支复用现有评估启动服务及必要的启动校验。必要时提取小型共用启动函数，避免复制事务、并发和配额逻辑。维持专用启动接口行为。
2. 先保持类型/任务名白名单校验，再验证执行参数。位置参数省略、为空或恰为 `[entity_id]` 时使用服务生成的规范参数；非空 kwargs 或其他位置参数返回 400，不允许参数选择另一个实体或覆盖执行配置。
3. 所有权与实体缺失沿用 404，非法状态及重复提交沿用 400，评估并发额度沿用 429。成功取得服务创建的关联任务后仍返回原有 AsyncTaskResponse 与 201，审计沿用评估启动规则。
4. 使用 SQLite 和真实路由验证发布时另一个会话已可读到关联。调用真实 worker 函数，替换付费模型执行边界，以确认任务能进入 running 并正常收尾。

## Risks / Trade-offs

- 新增依赖可能影响只挂载 tasks 路由的测试应用；同步补齐依赖或测试夹具，并执行现有端点与白名单回归。
- 避免在返回时重新使用存在 Celery 同步副作用的任务查询；读取服务创建的确切任务，不额外创建或发布任务。
- 原子性与发布失败处理沿用已有服务，不创建新事务协议。数据库结构和部署方式不变。

## Validation

覆盖自有草稿、他人及不存在实体、非 pending、重复提交、参数不一致、失效凭据、并发额度，以及发布前关联和真实 worker 执行；运行相关 API、评估提交、任务授权测试及改动文件格式检查。测试替换 broker 发布与模型执行边界，不依赖生产队列或真实模型。
