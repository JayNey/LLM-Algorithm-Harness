## MODIFIED Requirements

### Requirement: 预算与预警管理

用户 SHALL 能查看与编辑预算（全局上限、按难度分配、超限动作 pause/downgrade）、查看使用量，并管理预警规则（阈值百分比、通知渠道、启停）。规则保存 SHALL 与后端 schema 对齐（threshold 1–100、channel 白名单）。界面 SHALL 说明 Slack/Webhook 使用规则中配置的目标，邮件投递依赖 worker 的 SMTP 配置；只有存在个人全局预算、启用规则且 Web 评估 worker 在成本检查边界触发时才会尝试投递。保存规则或预算不代表投递成功，没有运行中的评估时不会后台轮询。界面 MUST NOT 暗示所有业务任务都会触发预警。站内预算预警 SHALL 表示阈值已被已知成本达到，外部渠道发送成功或失败 SHALL 通过既有预警投递历史的状态列分别显示，二者 MUST NOT 被描述成同一次成功。

#### Scenario: 预算编辑生效

- **WHEN** 用户修改全局上限或难度分配并保存
- **THEN** 使用量与上限展示随之更新，非法输入被本地拒绝

#### Scenario: 预警规则管理

- **WHEN** 用户新增/启停/删除预警规则
- **THEN** 列表反映最新状态，且界面准确说明规则所用渠道及投递触发条件

#### Scenario: 规则保存不等于成功投递

- **WHEN** 用户保存启用规则，但没有个人全局预算、运行中的 Web 评估或可用 worker 配置
- **THEN** 界面不声称通知已发送，并说明投递可能尚未触发或失败

#### Scenario: 邮件渠道依赖 SMTP worker 配置

- **WHEN** 用户选择邮件渠道
- **THEN** 界面说明收件人来自规则目标，SMTP 主机与认证配置必须由部署环境提供给 worker

#### Scenario: 站内通知保持 Mock

- **WHEN** 用户查看预算预警页或站内通知中心
- **THEN** 页面把站内阈值预警和外部渠道发送结果分成两种结果，不把规则保存或发送失败写成站内通知已成功发送，也不再把站内通知标为 Mock

#### Scenario: 显示实际外部投递状态

- **WHEN** 用户查看包含实际投递结果的预算预警历史
- **THEN** 同一表格按规则区分投递成功和失败，刷新后仍显示持久化结果

#### Scenario: 初始读取延迟或失败

- **WHEN** 预算读取尚未完成、被取消或返回错误
- **THEN** 表单仅在成功读取后允许编辑和保存，读取失败时提供重试

#### Scenario: 独立更新全局上限

- **WHEN** 用户仅修改全局上限并保存
- **THEN** 请求只包含全局上限，已保存的难度上限和超限动作保留，表单按保存响应回填；旧版仅全局预算和空难度配置均可编辑

#### Scenario: 单独修改或清除难度上限

- **WHEN** 用户修改或清除一个已读取的难度上限
- **THEN** 其余已读取的难度上限保留，表单以服务端响应为准

#### Scenario: 预算超限动作选择与持久化

- **WHEN** 用户编辑预算超限动作
- **THEN** 表单只提供暂停（`pause`）与降级模型（`downgrade`），且不可清除。保存切换后的任一动作时，保存响应、表单回填、硬刷新和 GET 读出的动作一致。

#### Scenario: 保存预算时省略未修改的动作

- **WHEN** 用户保存其他预算字段且未选择新的超限动作
- **THEN** PATCH 省略动作字段。已有预算保留原动作，首次建立预算采用默认的暂停动作，表单以服务端响应为准。
