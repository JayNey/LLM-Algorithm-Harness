## 修复方案

在评估恢复中取消只保护 `pending` 状态的限制；实验和基准恢复中同样取消此限制，并让活跃 AsyncTask 集合包含 `paused`，与评估既有语义一致。对于有活跃任务关联的业务记录，API 启动无权推断 worker 已停止，不改动状态、错误信息、时间戳、进度或关联。

保留无关联或关联任务已经结束的遗留在途记录的失败恢复行为，保留终态和暂停业务记录。保持实验完成回写必须仍为 `running` 的守卫，避免破坏既有暂停/取消语义；通过消除 API 误写，使正常 worker 可以持久化 `output_dir`、`completed_at` 和 `completed` 状态。

## 验证设计

单一测试文件对三个服务和 AsyncTask 状态做参数化覆盖：活跃关联、无关联、终态关联，以及已结束/暂停的业务记录。另通过实际 Celery 实验任务函数、真实数据库与新 API lifespan，模拟 runner 执行过程中启动另一个 API 实例；确认 worker 收尾成功且实验结果可查询。模型执行与认证密钥解析使用本地替身，不连接 broker 或外部模型。

## 边界

本次不新增 worker 失联检测或超时机制。活跃持久化 AsyncTask 由既有任务生命周期管理；API 重启本身不构成 worker 失败证据。数据库 schema 规格中的“被中断的在途任务”仍指没有活跃异步执行关联的遗留任务。
