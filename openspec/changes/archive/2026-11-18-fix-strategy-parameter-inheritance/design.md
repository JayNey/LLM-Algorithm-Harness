# 技术设计

## Context

动机与边界见 proposal.md。当前 StrategyBase.generate 用 model_fields_set 决定 temperature/max_tokens 是否覆盖模型，而三条 service 的普通 model_dump 丢失这一语义；TaskService.config_fingerprint 的完整 dump 同样会碰撞。ToT 构造器只读独立参数，Harness 仅传 StrategyConfig；过滤器缺少四个搜索字段。

## Decisions

1. 三个 service 使用保留显式字段的策略序列化；核对 worker 重建、配置快照、实验元数据等再序列化边界，保证嵌套策略同样保留语义。仅针对有继承契约的字段处理，避免全局修改默认值或误删用户填写的默认值。
2. ToT 构造器统一合并配置控制字段、既有默认值及显式构造器覆盖值。显式构造器值优先，其次 custom_params，最后默认值。使用可区分“未传入”的参数方式，严格验证类型与边界；正整数拒绝布尔和小数，阈值拒绝布尔、字符串及 NaN/无穷。
3. StrategyBase 既有控制字段过滤集合增加四个搜索字段，保留 top_p 等供应商选项。通过真实 LLMClient 搭配模拟 SDK 核对请求与 effective_params，不仅测过滤 helper。
4. 配置指纹纳入策略覆盖的显式性，保留其他字段已有规范化及脱敏契约；搜索参数继续参与任务/组合身份。审查阶段 3 引入的复用边界，必要时更新语义版本以拒绝无法证明兼容的旧检查点，保留旧产物供读取。LLM 响应缓存继续按实际供应商请求身份构键。
5. 历史数据库配置无可靠显式字段信息：将已存值视为显式配置，不做数据迁移；文档说明重新保存并省略字段可启用继承。

## 验证策略

- A：用真实 SQLite 业务保存/加载实验、A/B、基准，覆盖模型温度 0.2、显式策略温度 0.7、非 2000 模型 token 限制、显式 2000、默认配置及历史记录。
- B：通过 Harness 工厂创建实例并运行小树，验证 1/1/dfs/0.9、默认配置、直接构造兼容与非法输入；不调用网络供应商。
- 集成：模拟 SDK 检查搜索字段过滤、合法 provider 字段保留、有效参数记录；任务指纹及检查点验证省略/显式默认值差异、搜索变化和旧结果隔离；运行相关现有测试与格式检查。
- 按三个 delta spec 逐场景核对；此 tweak 配置 direct/direct/off，不要求独立审查，但保留最终 diff 自检。

## 风险与兼容

历史配置无法还原用户原始输入 → 保留原值并说明兼容策略。指纹修正导致旧检查点不可恢复 → 明确报错并保留历史结果。额外文件数来自三个保存入口及共用参数/复用逻辑和回归测试 → Build 范围复核时按 Runtime 确认，不拆成遗漏验收的局部修复。不改变搜索算法和全局生成默认值。
