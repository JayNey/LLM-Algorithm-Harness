## Context

当前系统支持独立的算法题评估，但缺少长期追踪机制。本设计实现学习曲线追踪功能，包括基准题目集管理、定期评估调度、历史数据存储、趋势分析和报告生成。参见 proposal.md 了解动机。

## Goals / Non-Goals

**Goals:**
- 建立固定的基准题目集定义和管理机制
- 支持手动和定时的评估调度
- 持久化历史评估结果并支持查询
- 生成时间序列趋势图和模型版本对比
- 提供完整的学习曲线报告

**Non-Goals:**
- 不自动订阅和检测模型版本更新
- 不使用机器学习模型进行性能预测（仅简单统计外推）
- 不追踪所有评估，仅追踪指定的基准题目集

## Decisions

### 1. 基准题目集存储格式
**决策**: 使用 JSON 格式存储基准题目集配置
**理由**: 
- 易于解析和验证
- 支持版本化和 frozen 标记
- 便于扩展元数据
**替代方案**: YAML（更易读但解析库依赖更重）

### 2. 历史数据存储结构
**决策**: 使用文件系统存储，按 `{timestamp}_{model-id}.json` 命名
**理由**:
- 简单直接，无需额外数据库依赖
- 便于版本控制和备份
- 文件名即索引，易于按时间和模型查询
**替代方案**: SQLite（增加依赖，对当前规模过重）

### 3. 趋势分析实现
**决策**: 使用 matplotlib 生成静态图表
**理由**:
- Python 生态标准可视化库
- 支持多种图表类型（折线图、对比图）
- 输出 PNG 可嵌入报告
**替代方案**: plotly（交互式但体积更大）

### 4. CLI 命令设计
**决策**: 扩展现有 harness CLI，添加 `benchmark` 子命令
**理由**:
- 保持一致的 CLI 接口
- 复用现有的评估框架
- 便于集成到现有工作流
**参数设计**:
- `--suite <name>`: 指定基准题目集
- `--compare`: 启用模型对比模式
- `--output <path>`: 指定报告输出路径

### 5. 定时任务实现
**决策**: 提供脚本和文档，不内置调度器
**理由**:
- 用户可使用系统 cron 或其他调度工具
- 避免引入后台服务依赖
- 更灵活的部署选项
**替代方案**: 使用 APScheduler（增加运行时依赖和复杂度）

## Risks / Trade-offs

**[Risk]** 文件系统存储在数据量大时查询性能下降  
→ **Mitigation**: 当前按月度/季度评估，数据量可控；未来可迁移到数据库

**[Risk]** 基准题目集变化导致历史对比失效  
→ **Mitigation**: frozen 标记强制题目集不可变；版本化管理

**[Risk]** 不同模型 API 变化影响对比公平性  
→ **Mitigation**: 记录模型版本和时间戳；文档说明对比的局限性

**[Trade-off]** 简单统计预测 vs. 机器学习模型  
→ 选择简单统计：初期数据少，线性外推足够；保持轻量

## Migration Plan

1. **Phase 1**: 实现基准题目集管理和手动评估
2. **Phase 2**: 添加历史数据存储和查询
3. **Phase 3**: 实现趋势分析和可视化
4. **Phase 4**: 生成完整报告
5. **Rollback**: 新功能独立模块，删除新增文件和命令即可回退
