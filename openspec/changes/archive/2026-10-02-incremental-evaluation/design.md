## Context

当前 `AlgorithmHarness` 在每次评估时加载完整的题目集并对所有题目执行策略。历史评估结果保存在 `results/` 目录下的独立 JSON 文件中，但没有关联数据集状态。需要引入增量机制，在数据集未变化时复用历史结果。

关键约束：
- 保持现有评估流程的准确性和可追溯性
- 增量检测必须准确识别题目变化（包括题面、测试用例的任何修改）
- 历史结果复用不能破坏报告的完整性
- 增量模式应该是可选的，不影响现有非增量评估

## Goals / Non-Goals

**Goals:**
- 准确检测数据集变化（新增、修改、删除题目）
- 仅评估变化的题目，显著减少重复评估时间和成本
- 无缝合并历史结果与新评估结果，生成完整报告
- 提供清晰的 CLI 接口，自动检测并提示增量模式

**Non-Goals:**
- 不支持策略配置变化的增量检测（策略参数改变需要全量重跑）
- 不支持跨不同模型的结果复用（模型变化需要重新评估）
- 不自动清理过期的历史记录（由用户手动管理）

## Decisions

### 1. 数据集指纹算法

**决策**：使用题目内容的 SHA256 hash 作为指纹，而非仅基于题目 ID

**理由**：
- 题目 ID 不变但内容变化的情况需要被检测到（如修正题面、更新测试用例）
- SHA256 提供足够的碰撞抵抗，确保准确性
- 性能开销可接受（题目数量通常在百级别）

**替代方案**：
- ❌ 仅使用题目 ID 集合的 hash：无法检测题目内容修改
- ❌ 使用文件修改时间：不可靠，git clone 会重置时间戳

**实现**：
```python
def compute_problem_fingerprint(problem: Problem) -> str:
    """计算单个题目的指纹"""
    content = json.dumps({
        "problem_id": problem.problem_id,
        "description": problem.description,
        "test_cases": problem.test_cases,
        # 包含所有影响评估的字段
    }, sort_keys=True)
    return hashlib.sha256(content.encode()).hexdigest()

def compute_dataset_fingerprint(problems: list[Problem]) -> dict[str, str]:
    """计算数据集指纹映射"""
    return {p.problem_id: compute_problem_fingerprint(p) for p in problems}
```

### 2. 历史记录存储结构

**决策**：使用 `results/.incremental/history.json` 存储运行历史索引

**结构**：
```json
{
  "runs": [
    {
      "run_id": "20261002_143022",
      "timestamp": "2026-10-02T14:30:22Z",
      "strategy": "vanilla",
      "model": "gpt-4",
      "dataset_fingerprint": {"problem_1": "abc123...", "problem_2": "def456..."},
      "result_path": "results/run_20261002_143022.json",
      "problem_count": 10,
      "success_count": 8
    }
  ]
}
```

**理由**：
- 集中索引便于快速查找匹配的历史运行
- 保留完整的运行元数据用于匹配验证
- 结果文件本身不变，保持现有格式

**替代方案**：
- ❌ 在每个结果文件中嵌入指纹：需要修改现有所有结果文件格式
- ❌ 使用数据库：增加依赖复杂度，对于百级别的运行记录过度设计

### 3. 增量检测策略

**决策**：三层检测机制

1. **完全匹配**：当前数据集指纹完全匹配某次历史运行 → 跳过评估，直接返回历史结果
2. **部分匹配**：识别变化的题目子集 → 仅评估变化的题目，合并历史结果
3. **无匹配**：无可用历史 → 全量评估

**匹配条件**：
- 策略名称和配置必须一致
- 模型名称必须一致
- 题目指纹匹配

**理由**：
- 分层检测覆盖最常见的使用场景
- 明确的匹配条件避免错误复用
- 保守策略确保结果准确性

### 4. CLI 集成设计

**决策**：添加 `--incremental` 标志，默认关闭

```bash
python -m src.main --config config.json --incremental
```

**行为**：
- `--incremental` 启用增量模式，自动检测并复用历史结果
- 未指定时使用传统全量评估（向后兼容）
- 增量模式下，在评估开始前输出检测结果：
  ```
  📊 Incremental mode: 8 problems unchanged, 2 new, 0 modified
  ⚡ Reusing results for 8 problems, evaluating 2 new problems
  ```

**理由**：
- 默认关闭确保现有脚本和 CI 不受影响
- 显式标志让用户清楚知道使用了增量模式
- 透明的输出建立信任

**替代方案**：
- ❌ 默认启用增量：可能在用户不知情的情况下复用过期结果
- ❌ 自动检测并提示：增加额外的交互复杂度

## Risks / Trade-offs

### 风险 1：指纹计算遗漏关键字段

**风险**：如果题目的某些字段影响评估但未包含在指纹中，会导致错误复用

**缓解**：
- 指纹计算包含 Problem 模型的所有核心字段
- 单元测试覆盖字段变化场景
- 文档明确说明哪些变化触发重新评估

### 风险 2：历史结果文件移动或删除

**风险**：history.json 指向的结果文件被移动或删除，导致增量失败

**缓解**：
- 在读取历史结果前检查文件存在性
- 文件缺失时回退到全量评估，记录警告日志
- 提供 `--verify-history` 命令验证历史索引完整性

### 风险 3：策略配置的隐式变化

**风险**：策略配置参数变化但未被检测到（如环境变量影响的超参数）

**缓解**：
- 在历史记录中保存策略配置的 JSON 序列化
- 匹配时比较配置的 hash
- 文档明确说明策略配置变化需要全量重跑

### Trade-off：存储开销

**权衡**：每次运行保存数据集指纹增加存储开销（每个题目约 64 字节 hash）

**接受理由**：
- 对于典型规模（100 题目 × 100 次运行），总开销约 640KB，可忽略
- 相比节省的评估成本，存储开销微不足道
- 用户可以手动清理旧历史记录

## Open Questions

1. **历史记录保留策略**：是否需要自动清理超过 N 天的历史记录？
   - 当前设计为手动管理，可以后续添加 `--cleanup-history` 命令

2. **并发运行支持**：多个增量评估同时运行时如何避免 history.json 冲突？
   - 初始版本使用文件锁，后续可以考虑分片存储或进程内缓存
