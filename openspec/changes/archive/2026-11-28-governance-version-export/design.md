# 技术方案

## 背景与边界

现有 `api_dataset_versions.payload` 保存所选题目的完整快照，版本详情经 `VersionProblem` 摘要化；不能用详情响应拼接完整导出。治理版本是已选题集，不应意外加入主库中未选题目。当前主库导出继续走原入口。

## 决策

1. 沿现有治理版本路由新增完整数据 JSON 和报告 JSON 下载，统一使用现有附件响应与 Cookie 身份验证，服务端按 `user_id + version_id` 读取快照。
2. 完整数据直接序列化已保存快照为可导入的 Problem 数组，不经摘要模型，也不读取当前主库来补字段。
3. 保存治理版本时构造真实已应用的标签和难度差异，记录 `problem_id`、原标签/新标签、原难度/新难度及批准选项。只记录实际改变的题目；未批准项与批准后没有实际差异的项不伪造变更。
4. 使用独立的版本报告存储，与快照同一事务保存，随版本保留策略一起清理，兼容现有版本表及调用者。历史版本没有报告时返回明确的“历史变更报告不可用”错误，不回溯推断。
5. 前端通过共享 HTTP 客户端下载 Blob，沿用会话刷新机制。下载绑定点击时所选版本；切换版本或账号后取消或忽略迟到响应，禁止将旧文件作为当前选择下载。按钮在详情尚未与当前版本匹配、加载或下载期间禁用，并展示实际错误。
6. 去重保存的版本复用完整数据导出；没有标签/难度报告的版本采用同一明确反馈，不扩展为去重审计报告。

## 风险与验证

- 完整字段被摘要丢失：以含隐藏测试、判题配置、入口和来源元数据的小型 Problem 验证 JSON 完整性及重新导入。
- 历史值漂移：保存后修改主库和相关记录，再核对报告保持不变。
- 用户越权和清理竞态：两个用户访问同一版本、未知 ID 与清理后的版本均不得泄露数据。
- UI 选择竞态：mock 延迟响应，实际切换版本与会话并检查请求和下载内容；保留从版本创建评估入口。
- 执行必要后端测试、前端类型检查、格式与 lint、客户端测试及浏览器 mock 验收，不要求付费 API 或全量评估。

## 兼容与回退

报告存储采用增量建表，不改写已有版本快照，历史缺失值明确反馈不可用。先部署后端兼容接口再部署前端；回退前端或后端时保留新增报告表，旧代码继续使用原版本表，不进行有损迁移。
