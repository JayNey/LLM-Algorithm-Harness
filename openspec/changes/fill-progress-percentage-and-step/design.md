## Context

任务记录已有 JSON 进度字段。导入 worker 会写入已处理数量、总数、百分比和一句汇总消息；实验和基准 worker 不写进度。暂停检查位于下一个组合、下一道导入题和下一道基准题之前。见 proposal.md 的 Why。

## Goals / Non-Goals

**Goals:**

- 在上述三个安全边界更新任务进度，使查询能看到百分比和当前步骤。
- 百分比与数量使用同一分母，并限制在 0 到 100。
- 当前步骤只保留定位所需的短标识。

**Non-Goals:**

- 不改评估任务的进度口径，也不新增 WebSocket。
- 不新增表或列，不改暂停和恢复行为。
- 不改导入作业进度接口已有的数量和百分比字段。

## Decisions

1. 进度继续写入任务记录已有的 JSON，字段为 `current`、`total`、`percentage`、`current_step`。不给导入作业表加列。导入作业接口因此不会多返回当前步骤；任务查询会返回。
2. 实验在每个组合开始前写入：`current` 为已完成组合数，`current_step` 为 `模型/策略/重复序号`。基准在每道题开始前写入：`current` 为已完成题数，`current_step` 为 `策略/题目标识`。这样百分比表示已完成比例，当前步骤表示即将执行的单元。
3. 导入沿用每 100 条以及最后一条的上报节奏。`percentage` 仍由已处理数除以总数得到，`current_step` 为这次上报的条目序号。避免为每一条都写一次任务记录。
4. 百分比在总数为 0 时为 0，其余先计算再限制到 0 到 100。暂停、完成和失败都不清除已写入的进度。
5. 这次改动同时碰到实验、导入和基准三个执行循环。用户选择继续 tweak：进度仍写在已有任务 JSON 上，三个循环用同一种字段，不另开完整设计流程。

## Risks / Trade-offs

- [导入当前步骤最多滞后 99 条] → 与现有进度上报节奏一致，避免大题库逐条写库。
- [当前步骤含模型名、策略名或题目标识] → 这些标识本来就出现在任务配置和日志中；不写入题目正文、上传内容或密钥。
- [实验并行时多个组合同时开始] → 进度记录最后一次提交的组合，不保证与所有并行组合一一对应。

## Migration Plan

只改变运行中任务的进度 JSON。旧任务没有这些字段时保持原样。回滚时停止写入新字段，已写入的 JSON 可继续被查询。
